# Implement PQ gossip on Silver’s existing fork-aware network path

Silver already recognizes the PQ fork, schedules its gossip digest, carries the originating `GossipDomain` on received messages, and checks fork-specific sizes before Snappy decompression. The main gaps are **two stale SSZ layouts and bounds, incomplete topic and subnet enforcement, and BLS assumptions in the beacon-state validation and local publication paths**. The largest share of the work is in `ssz` and `beacon_state`, alongside the four crates named in the request. This is a static comparison against the local specification. ## 1. Correct the PQ wire format first

| Uncompressed gossip message | Current Silver maximum | PQ spec maximum |
|---|---:|---:|
| `SignedAggregateAndProof` | 1,068,549 B | **1,055,231 B** |
| `AttesterSlashing` | 4,194,584 B | **2,621,720 B** |
| `SignedExecutionPayloadBid` | 199,240 B | **199,240 B** |

The first two differences affect decoding and signing roots. Silver’s PQ `AggregateAndProof` still serializes and hashes a 1,024-byte VRF `selection_proof`. The current spec removes that field and carries `aggregator_index`, `aggregate`, and the STARK `proof`. Silver’s PQ attestation also reads eight bytes of `committee_bits` where the spec uses two, and its bitlist and indexed-attestation checks use the old maximum participant count. Update the views, offsets, participant limits, tree hashing, and fixtures together. Changing only the gossip size constants would still reject valid aggregates or verify the wrong signing root. The existing PQ bid and signed proposer-preferences views can be reused. ## 2. Enforce the topic set and 16 subnets per fork digest

- **Topic admission.** `GossipTopic::is_removed_in_pq` already identifies voluntary exits, BLS-to-execution changes, sync committee contributions, sync subnets, and both light-client topics. Peer-manager code uses the predicate, but `ActiveDomains::parse` accepts a recognized name on either active digest, and `current_wire` constructs a local topic without checking format support. Apply the same domain-aware predicate on receive, subscription processing, and local publication. Include the subnet ID in that predicate so `beacon_attestation_16` through `_63` remain usable on the old digest only. Exercise both digests during the existing fork-overlap window. [Topic policy](/home/vlad/repoz/pq-silver/crates/common/src/gossip.rs:143) · [Peer filtering](/home/vlad/repoz/pq-silver/crates/peer/src/manager/peers.rs:50) · [Wire parsing and publication](/home/vlad/repoz/pq-silver/crates/gossip/src/handler.rs:646)
- **Subnet assignment and advertisement.** `ATTESTATION_SUBNETS_PQ = 16` exists, but duty assignment still takes modulo 64, and `NodeId::attestation_subnets` shuffles a six-bit prefix over 64 entries. Make both calculations fork-aware. PQ uses `ceil(log2(16)) + ATTESTATION_SUBNET_EXTRA_BITS` for the prefix and modulo 16 for the subnet. Apply this to API duties, local publication, inbound attestation validation, and long-lived subscriptions. Recompute long-lived subnets at activation and subscription-period rotation, including on a running node. Keep ENR `attnets` and `MetaData.attnets` eight bytes wide, with only bits 0–15 eligible at PQ, including when explicit subscriptions are configured. - **Fork schedule and RPC.** Reuse Silver’s PQ activation, digest, and overlap machinery. One prerequisite difference is that Silver’s schedule goes directly from Gloas to PQ, while the spec’s `compute_fork_version` includes EIP-8483 between them. A network that schedules that intermediate fork needs its epoch and version represented for correct digests and signing domains. Silver’s RPC request enum already omits light-client methods. Existing block and payload-envelope RPCs need PQ-aware decoding wherever their responses enter shared validation or sync paths. ## 3. Connect PQ decoding and verification to the live handlers

Use the received `NewGossipMsg.domain.format()` to select the decoder **before reading a slot, offset, or signature**. This matters at the fork boundary and for blocks in particular, because a PQ signature moves the start of the block message. Today the block path reads the legacy view, and the gossip dispatcher and batched vote path lead to BLS-oriented handlers. The shared prerequisites are validator and builder XMSS keys, duty-specific leaf derivation, PQ signing roots, and STARK statement verification. ## 4. Acceptance tests

1. Regenerate SSZ and signing-root fixtures from the current spec. Test all three exact maxima and one byte over, the two-byte committee field, and rejection of the obsolete aggregate layout.
2. Run a Gloas → PQ transition through the real gossip and peer paths. Cover inbound messages, local sends, subscriptions, subnet IDs 15 and 16, and ENR/metadata updates without restarting.
3. For each signed topic, exercise a valid message, a wrong key or leaf, and the specified `IGNORE` versus `REJECT` outcome. Include a bad aggregate STARK, an aggregate requiring state advancement, a block over an operation limit, and a builder’s second valid improving bid when its limit permits one.
4. Exercise the same PQ block and envelope through gossip and RPC sync, plus local block and attestation submission through the API. Verify that accepted messages relay on the correct digest and that invalid messages do not populate valid-message caches.
